# 04 — 写下「后端支持多 idol、客户端各自限制守护数量」的架构决策

**What to build:** 一份 ADR，记录本项目在守护关系上的多端策略：数据模型与后端 API 支持一个用户守护多位 idol，但每个客户端自行决定允许的数量上限——微信小程序限制为 1 位，未来的 iOS/Android 客户端可放开。

这个决策不好逆转，且它的动机在代码里完全看不出来。六个月后有人看到后端支持多个守护关系、小程序却只让选一位，第一反应会是「小程序少实现了一个功能」并去补全它，从而绕过微信订阅消息额度这个真实约束。

**Blocked by:** None — can start immediately.

**Status:** ready-for-agent

- [ ] 记录决策本身：后端多守护、客户端限额
- [ ] 记录动机：微信一次性订阅消息的额度不随守护数量增长，小程序端放开多守护会让推送体验劣于单守护
- [ ] 记录该约束不适用于原生 app（走系统推送通道，无额度概念）
- [ ] 记录被否决的方案：小程序端也放开多守护、按轮询分配唯一额度
- [ ] 说明守护数量上限属于服务端策略而非客户端硬编码
