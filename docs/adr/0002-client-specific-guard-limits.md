# 由服务端按客户端类型限制守护数量

目标架构以 `idr_user_guard` 表达一个用户守护多位 idol，并由服务端按受信任的客户端类型执行数量上限：微信小程序最多守护 1 位；未来使用系统推送、没有微信订阅消息额度限制的原生客户端可以放开多守护。数量限制不得只硬编码在客户端，否则用户可绕过界面直接调用 API。

微信一次性订阅消息额度不会随守护数量增加。否决“小程序也支持多守护、按轮询分配唯一额度”的方案，因为它会让不同 idol 争抢同一额度，导致提醒结果不可预测且明显弱于单守护体验。

数据模型与读路径已经落地：Worker 推送与 API 读路径均从 `idr_user_guard` 读取，`idr_user` 上的单值字段及其索引已由 V7 删除，关联表是守护关系的唯一事实来源。

尚未实现的是「按客户端类型执行上限」本身：`PUT /v1/me/idol` 当前对所有调用方硬编码单守护（替换唯一的守护关系）。在只有小程序一种客户端时，这与本决策要求的行为等价且同样由服务端强制，因此不构成可绕过的漏洞，只是缺少按类型区分的能力。

客户端类型不得从请求头等客户端可控输入判断，否则用户可直接伪造。正确做法是在签发会话时记录：微信登录端点用一次性 code 向微信换取 openid，这条路径本身即证明调用方是小程序，把类型写在 `idr_user_session` 上，请求侧只读不写。该实现推迟到真正出现第二个客户端时进行——在原生客户端的登录方式确定之前，提前设计的类型标签大概率要返工。
